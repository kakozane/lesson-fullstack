## 课程定位

听众已经会 Vue3 和 Go 基础。本课不讲 Go 接口实现、不搭建 Vben、不从头讲响应式语法。使用现成 API，在已有后台中把一个业务模块做完整。

完成后，听众应能解释并实现：

1. 筛选条件、页码、表格结果如何协作。
2. 新增与编辑共用弹窗时，如何回填、校验、重置与提交。
3. 单条与批量操作如何关联确认、禁用、刷新和选择状态。
4. 失败与异步乱序出现时，如何保持页面状态正确。

完整答案保留在 apps/admin，课堂初始版已准备在 apps/starter：菜单和登录可用，业务页面仅有标题。现场在 starter 编写，admin 用作参考和回退，启动方式见 `08-课堂初始版使用说明.md`。初始版没有业务静态模板，为控制时间可课前准备模板片段，现场重点绑定状态和事件。听众全程跟敲时，将“未保存提醒”和“请求竞态实现”改为源码讲解。

## 00～05 分钟：从最终效果出发

讲师开场可以说：

> 今天我们不从安装框架开始。这个后台和 Go 接口已经准备好，我们要完成的是一个真实业务页面：用户修改商品后，数据、界面和操作状态都要正确。

现场操作：

1. 搜索“鼠标”，展示分类和上下架条件。
2. 新建一件商品，编辑价格，再批量下架。
3. 故意使用重复编码，展示后端错误提示与保留的表单。

只展示两个接口：

```text
GET /api/products?page=1&pageSize=10&keyword=鼠标&status=0
POST /api/products
```

说明三个约定：

- `status=0` 是下架，空字符串表示全部，不能用真值判断丢掉 0。
- 金额字段 `priceCents` 是整数分，29.90 元提交 2990。
- 接口返回 `{ code, data, message }`，现成 requestClient 已取出 data。

不讲 Go handler、SQL 驱动和鉴权实现。它们是这节课的已知条件。

## 05～17 分钟：列表不只是调用一次接口

### 第一步：划分两份条件

打开 `use-product-list.ts`。

- `filters`：用户正在输入的表单条件。
- `query`：已经应用到列表的请求条件，包含 page 和 pageSize。

为什么分开：用户输入新关键词但没点击查询时，翻页仍然应该使用上一次查询条件。否则表格看似只翻页，实际上悄悄换了搜索条件。

分类和状态变化立即执行 search；关键词点击查询或按 Enter 后执行；清空关键词立即查询。

现场编写主线：

```ts
function search() {
  Object.assign(query, filters, {
    keyword: filters.keyword.trim(),
    page: 1,
  });
  return load();
}

function changeSize(pageSize: number) {
  Object.assign(query, { pageSize, page: 1 });
  return load();
}
```

强调：筛选改变和每页条数改变都回第一页，普通翻页只改 page。

### 第二步：连接页面

打开 `index.vue`，绑定：

- 搜索表单的 submit → search。
- 分类和状态的 change → search。
- 重置 → reset。
- 分页的 current-change / size-change → changePage / changeSize。

筛选不要再用前端 `filter()` 过滤当前页，否则 total、页码和结果会失去一致性。

### 第三步：现场验证

1. 翻到第 3 页，选择“已下架”，观察回到第 1 页。
2. 在 Network 中确认请求包含 `status=0`。
3. 点击重置，条件变为空，恢复全部结果。
4. 输入不存在的关键词，展示空状态。

互动问题：如果把 `if (status)` 写进参数拼接，会发生什么？答案：下架筛选值 0 被当成假值丢失。

## 17～32 分钟：一套弹窗支持新增与编辑

### 第一步：明确父子职责

父页面管理：弹窗是否打开、编辑哪条商品、保存后重新加载列表。

子组件管理：表单草稿、校验、保存中状态、取消时是否有未保存修改。

这里不需要新增 Pinia store。商品表单只服务当前页面，不是跨页面共享状态。

通信关系：

```text
父页面 product + modelValue → 表单
表单 update:modelValue → 关闭弹窗
表单 saved → 父页面重新加载列表
```

### 第二步：回填与重置

打开 `product-form.vue` 中监听 `modelValue` 的 watch。

- 编辑：逐字段复制当前商品，把 priceCents / 100 显示为元。
- 新增：重新填入全部默认值，包括空名称、空编码、库存 0 和下架状态。
- nextTick 后 clearValidate，避免上一次校验提示残留。

不要直接把 row 引用当作表单：用户点取消之前，表格可能已经跟着输入变化。完整代码使用独立的 reactive 草稿对象。

现场先打开编辑，再取消，接着打开新增，确认没有残留数据。

### 第三步：提交顺序

现场编写 submit 的关键流程：

```text
检查 saving → 设置 saving → 表单校验 → 构造 ProductInput
→ 根据是否有 product 选择 POST / PUT
→ 成功提示 → 关闭弹窗 → 通知父页面刷新
→ finally 解除 saving
```

重点讲四处：

1. saving 在校验开始前设置，避免连续点击发出两个保存。
2. 校验失败也是正常交互，不关闭弹窗。
3. 请求失败保留输入；统一请求层提示，不在页面重复弹两次错误。
4. 不把整个表单直接提交：价格转换成分，只提交契约允许的字段。

保存按钮等待响应时显示“正在保存”，表单和取消按钮禁用，关闭按钮隐藏。若请求超时，输入保留、按钮恢复；超时不代表服务端一定未写入，新增前先查询该编码，避免盲目重试。编辑重试使用相同商品 ID 和完整字段。

金额转换：

```ts
priceCents: Math.round(form.price * 100)
```

输入限定两位小数，乘 100 后四舍五入，后端再验证整数与范围。整数分仅解决本课金额存储和显示问题，不展开税率、汇率、复杂结算。

### 第四步：现场联调

- 空表单提交，看到必填错误。
- 输入合法商品保存，列表出现新商品。
- 编辑为 29.90 元，刷新页面仍然是 29.90。
- 改成已有编码 SP-0001，保存失败、弹窗和输入保留。

时间紧时，“未保存提醒”的实现只展示结果，放到课后阅读。

## 32～42 分钟：批量操作的重点是状态一致

打开 `index.vue` 的 selected、operating、changeStatus 和 saved。

先实现单条上下架，再复用相同接口处理选中 ID 数组，不另外设计一套批量服务。

```ts
const ids = row
  ? [row.id]
  : selected.value.map((item) => item.id);
```

完整流程：

1. 没有选择不发请求，按钮禁用。
2. 点击时固定本次操作的 ID 集合。
3. 打开确认框，锁定本次操作，避免连续点击叠出多个确认框。
4. 确认后提交，取消则解除锁定。
5. 成功后清空选择，并按当前筛选重新查询。
6. finally 解除操作中状态。

为什么不在前端直接逐行修改 status：当前筛选可能是“上架中”，下架后这些商品应该消失，总数也会变。重新查询比手工维护列表和 total 更容易保证一致。

本课选择只保留当前页，不保留跨页选择。切页或重新加载清空表格数据，旧选择随之清空；界面明确标注“仅当前页”。

现场演示：筛选“上架中” → 选择两件 → 批量下架 → 确认列表减少、总数更新、选择归零。

删除操作沿用同样顺序，但使用明确的不可恢复提示。不在课堂中增加批量删除。

## 42～51 分钟：让异常成为设计的一部分

### 1. 请求乱序（4 分钟）

讲一个时间线：

```text
A：查询“鼠标” ────────────── 返回旧结果
B：查询“键盘” ─── 返回最新结果
```

如果 A 最后回来就覆盖页面，输入框和结果不一致。

展示 `use-product-list.ts` 的 requestId：每次请求递增序号，响应成功、失败和 finally 都检查当前序号。特别指出：只保护数据赋值还不够，旧请求也不能提前关闭新请求的 loading。

```ts
const current = ++requestId;
const result = await getProducts({ ...query });
if (current !== requestId) return;
```

课堂不依赖网络恰好出现乱序。运行定向测试，展示两个 Promise 被人为安排以相反顺序完成：

```sh
# frontend 目录
corepack pnpm exec vitest run apps/admin/src/composables/use-product-list.test.ts
```

这个实现忽略过期响应，不取消底层请求。对于本课的手动查询已足够；若加入高频实时搜索，再考虑防抖和 AbortController。

### 2. 失败不是空结果（2 分钟）

停掉 Go 服务，点“刷新列表”。看到错误反馈与重新加载入口，而不是误认为“没有商品”。恢复 Go 后会话失效，需要重新登录；这一点提前告诉听众。

更平稳的演示方式：浏览器 Network 暂时设为 Offline，点击刷新；恢复 Online 后点重新加载。该方式不会重启服务器，不会使会话失效。

### 3. 删除末页最后一条（2 分钟）

使用独立测试关键词查出少量商品，观察服务端返回的 page。后端会把超出范围的页码归到最后一个有效页，前端必须采用响应的 page，不盲目保留旧页码。

真实接口回归与 Gin 改造后的浏览器复验都已覆盖该场景：用 11 条独立测试商品、每页 10 条，删除第 2 页唯一商品后回第 1 页。课堂可提前准备独立测试数据，不需要删除种子商品来凑页数。

### 4. 未保存修改和操作中离开（1 分钟）

展示表单修改后点击取消的确认框、保存时禁用关闭、路由离开保护。浏览器关闭提醒使用浏览器标准提示，不保证显示自定义文字。

## 51～55 分钟：沿一次保存回顾

带听众从 UI 沿调用顺序走一遍：

```text
点击编辑
→ 父组件传入商品
→ 子组件建立草稿
→ 校验并转换请求字段
→ API 调用 Go
→ MySQL 持久化
→ 成功后子组件发出 saved
→ 父组件按当前条件重新查询
→ 表格和总数一起更新
```

最后让听众回答三问：

- 为什么表单草稿不直接指向表格 row？
- 为什么批量下架后重新查询，而不是只改 tag 颜色？
- 为什么旧请求的 finally 也要检查序号？
