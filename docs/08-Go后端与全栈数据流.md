# 从商品管理理解 Go 后端与全栈数据流

本文结合当前项目的 Gin、GORM 和 MySQL 实现，解释一次请求如何完成，以及前后端为什么需要共同约定字段、校验和错误处理。阅读时不需要重新编写接口。

建议先完成[商品管理实战](03-商品管理实战.md)的环境准备；字段细节可查阅[商品管理接口与 TypeScript 类型](04-商品管理接口与TypeScript类型.md)。以下路径均相对于项目根目录，代码片段用于说明对应实现。

## 1. 点击“保存商品”之后发生了什么

以新增商品为例，前端提交：

```http
POST /api/products
Authorization: Bearer <登录获得的令牌>
Content-Type: application/json
```

```json
{
  "name": "无线鼠标",
  "sku": "CLASS-MOUSE-001",
  "categoryId": 1,
  "priceCents": 2990,
  "stock": 12,
  "status": 0,
  "description": "商品说明"
}
```

请求的执行顺序：

```text
商品表单 submit()
  → createProduct(data)
  → requestClient 发出 HTTP 请求
  → Gin 匹配 POST /api/products
  → Auth 中间件验证登录令牌
  → Handler.Create 解析 JSON
  → ProductService.Create 校验业务字段和分类
  → ProductRepository.Create 写入 MySQL
  → 统一响应 code、data、message
  → 前端关闭弹窗，触发 saved，重新查询列表
```

| 阅读位置 | 关注的函数或行为 |
|---|---|
| `frontend/apps/admin/src/views/products/product-form.vue` | `submit()`：校验、组装字段、请求、关闭与通知 |
| `frontend/apps/admin/src/api/products.ts` | `createProduct()`：请求方法与路径 |
| `backend/router/admin/router.go` | `products.POST("", app.Product.Create)`：路由入口 |
| `backend/middleware/auth.go` | 登录验证，通过后才进入业务 Handler |
| `backend/internal/product/admin/handler/product.go` | `Create()`：解析请求并调用 Service |
| `backend/internal/product/admin/service/product.go` | `Create()`、`validate()`、`validateCategory()` |
| `backend/internal/product/repository/product_repository.go` | `Create()`：数据库写入 |
| `backend/internal/dto/response/response.go` | `Success()`、`Fail()`：统一返回 |

接口成功时，HTTP 状态为 200，响应为：

```json
{
  "code": 200,
  "data": null,
  "message": "保存成功"
}
```

新增接口没有返回商品对象。前端等待保存成功后再次查询列表，获得数据库中的最新结果。失败时保留表单输入，不关闭弹窗，也不显示成功提示。

## 2. Gin 做什么，为什么还需要分层

Gin 负责 HTTP 路由、中间件、请求上下文和响应输出。它不会自动知道商品价格的范围、分类是否有效，或 SKU 是否允许重复。这些规则由项目代码实现。

| 层 | 负责什么 | 本项目示例 |
|---|---|---|
| Router | 请求方法、路径和公共中间件 | 哪些接口必须登录 |
| Handler | HTTP 输入输出 | 读取 Query、Path、JSON，返回统一响应 |
| Service | 业务规则与流程 | 校验商品、分类、批量数量，转换业务错误 |
| Repository | 数据库操作 | 查询、分页、更新、事务 |

以新增接口为例，Handler 不直接写 SQL：

```go
var req dto.SaveRequest
if !httpx.DecodeJSON(c, &req) {
    return
}
if err := h.products.Create(c.Request.Context(), req); err != nil {
    response.Fail(c, err)
    return
}
response.Success(c, nil, "保存成功")
```

这里的 `c.Request.Context()` 会沿调用链传到 GORM，用于传递请求取消等信号。它不负责保存登录令牌或业务数据，也不等于一次数据库事务。

分层的直接价值是方便定位问题：

- 请求没有进入 Handler：检查 URL、HTTP 方法、代理和鉴权。
- 请求 JSON 解析失败：检查字段名、类型和请求格式。
- 返回“请选择有效分类”：检查 Service 校验和分类 ID。
- 数据库写入失败：检查 Repository、数据库约束和后端日志。
- 保存成功但页面没变化：检查前端是否刷新，当前筛选是否排除了该商品。

## 3. DTO、数据库实体与前端类型有什么区别

DTO 描述接口接收或返回的数据；Entity 描述数据库映射；TypeScript 类型描述前端如何使用数据。三者职责不同，不必完全相同。

例如分类关联：

```text
categories 表：id、name
products 表：category_id
         ↓ GORM Preload("Category") 加载关联
列表响应：categoryId、categoryName
         ↓
表格展示 categoryName，编辑表单保存 categoryId
```

相关文件：

- `backend/internal/product/admin/dto/product.go`：SaveRequest、ListQuery、Product、PageResult。
- `backend/internal/product/entity/product.go`：Product、Category 的数据库映射。
- `frontend/apps/admin/src/api/products.ts`：ProductInput、Product、ProductQuery、Category。

Go 字段 `CategoryID` 的 JSON 标签是 `json:"categoryId"`，因此接口对外使用 categoryId。数据库映射使用 category_id，名称由分类表管理。

新增和编辑只提交 ProductInput 中的字段，不能直接把整行商品传回去。列表里的 id、updatedAt、categoryName 是展示或标识信息，不属于保存请求；本项目会拒绝未知 JSON 字段。

## 4. 前端已经校验，后端为什么还要校验

前端校验能及时提示用户，但不能保证所有请求都来自当前页面。请求可以由其他客户端发起，也可能来自旧版前端。

后端必须独立确认：

- 商品名称和描述的长度是否符合要求。
- SKU 格式是否正确。
- categoryId 是否为正整数，并且在分类表中存在。
- 价格、库存、上下架状态是否在合法范围。
- 批量请求的 ID 是否有效、是否重复、数量是否超限。

参数格式与业务规则分别处理：

| 情况 | 检查位置 |
|---|---|
| JSON 损坏、字段类型错误、未知字段、多个 JSON 对象 | `backend/internal/pkg/httpx/param.go`：`DecodeJSON()` |
| 名称为空、库存为负数、状态不是 0 或 1 | Service 的 `validate()` |
| 分类 ID 不存在 | Service 的 `validateCategory()` 查询 Repository |
| SKU 重复 | MySQL 唯一约束，Service 转换成“商品编码已存在” |

SKU 唯一性不能只依赖“先查询是否存在”：两个请求可能同时查询到不存在。数据库唯一约束负责最终保证，本项目将 MySQL 1062 错误转换成可理解的业务提示。

## 5. 为什么价格传 2990，而不是 29.90

本项目约定金额以“分”为单位传输和存储：

| 位置 | 值 |
|---|---|
| 页面显示 | 29.90 元 |
| JSON priceCents | 2990 |
| Go 类型 | int64 |
| MySQL 字段 | price_cents，BIGINT |

前端回填：

```ts
price: product.priceCents / 100
```

前端提交：

```ts
priceCents: Math.round(form.price * 100)
```

这样持久化和接口使用整数，避免把二进制浮点小数直接当作金额存储。本项目限定两位小数和金额范围，Go 再校验整数分必须在 1～99999999 之间。

这并不意味着所有金额计算都可随意使用浮点数。涉及税费、折扣、多币种或更高精度时，需要单独约定精度和舍入规则；这里的重点是前后端统一金额单位。

## 6. 为什么 status 使用 *int，而 stock 使用 int

Go 的 int 零值是 0。若 status 定义为 int，JSON 没传 status 时得到 0，明确传 `"status": 0` 时也得到 0，无法区分两种情况。

当前请求结构使用：

```go
Status *int `json:"status"`
```

| 请求内容 | Go 中的结果 | 当前行为 |
|---|---|---|
| 没有 status | nil | 拒绝 |
| `"status": null` | nil | 拒绝 |
| `"status": 0` | 指向 0 的指针 | 合法，下架 |
| `"status": 1` | 指向 1 的指针 | 合法，上架 |
| `"status": 2` | 指向 2 的指针 | 拒绝 |

校验先判断是否 nil，再解引用：

```go
if p.Status == nil || (*p.Status != 0 && *p.Status != 1) {
    return bad("商品状态必须为 0 或 1")
}
```

stock 使用 int，是因为当前接口允许默认库存 0；未传和传 0 都会得到 0。如果以后要求必须显式填写库存，可以同样用指针区分。

前端也要保留这个区别：库存 0、下架 0 都是有效业务值，不能用 `if (value)` 或 `value || 默认值` 把它们当成未填写。

## 7. 为什么 GORM 更新使用 map

在本项目使用的 GORM 更新方式中，`Updates(struct)` 默认会忽略结构体中的零值字段。库存 0、下架 0、空描述恰好都是需要保存的合法值。

因此 Repository 显式传入 map：

```go
Updates(map[string]any{
    "name":        p.Name,
    "sku":         p.SKU,
    "category_id": p.CategoryID,
    "price_cents": p.PriceCents,
    "stock":       p.Stock,
    "status":      p.Status,
    "description": p.Description,
})
```

实际实现还会更新 updated_at。map 明确列出要更新的字段，零值也会参与更新。

另一个可选方式是显式选择结构体更新字段，但当前项目统一使用 map，阅读时只需掌握这一条路径。

排查“前端传了 0，数据库没变化”时，不要马上怀疑 Vue 双向绑定。先看 Network 请求，再看 DTO 是否收到值，最后检查 ORM 的更新方式。

## 8. 分类筛选为空，后端如何理解

前端默认或清空筛选后不传 categoryId：

```text
GET /api/products?page=1&pageSize=10
```

选择分类后传数字 ID：

```text
GET /api/products?categoryId=2&page=1&pageSize=10
```

后端 ListQuery 的 CategoryID 为 int64，未传时为 0。Repository 只在其不为 0 时增加分类条件。这是后端内部表示“不筛选”的方式，不要求前端发送 0，更不需要发送“全部分类”字符串。

列表查询和保存的规则不同：列表允许不限制分类，新增和编辑必须填写一个真实存在的分类 ID。

## 9. HTTP 状态码与 JSON code 为什么分开

HTTP 状态码属于协议，JSON code 是项目自己定义的响应字段，与 data、message 同级。

| 情况 | HTTP 状态 | JSON code |
|---|---:|---:|
| 成功 | 200 | 200 |
| 商品不存在、SKU 重复、参数或分类不合法 | 400 | 400 |
| 未登录、凭证错误、会话过期 | 401 | 401 |
| API 路径不存在 | 404 | 400 |
| 请求方法不支持 | 405 | 400 |
| 未预期的数据库或服务错误 | 500 | 400 |
| 健康检查发现数据库不可用 | 503 | 400 |

这是本项目采用的约定，并非所有系统都必须如此。域名解析失败通常发生在 HTTP 请求到达服务之前，不会由本项目返回 HTTP 404。

可预期的业务错误返回中文 message；未预期错误写入后端日志，对外返回“服务暂时不可用，请稍后重试”，不把底层数据库错误直接展示给用户。

## 10. 批量上下架为什么用事务

`ProductRepository.BatchStatus()` 在事务中查找并锁定目标商品，确认实际数量与请求 ID 数量一致，再统一更新状态。

例如选择 3 件商品，其中一件已被其他操作删除：本项目返回“部分商品已删除，请刷新后重试”，整批失败，避免出现只更新两件却让前端以为全部成功的情况。

事务主要保证这一组数据库操作的整体性。前端 operating 状态防止当前页面重复操作，后端事务处理数据库一致性，两者解决的问题不同。

## 11. go run . 如何启动服务，配置从哪里来

本项目启动顺序见 `backend/main.go`：

```text
config.Load()
  → bootstrap.InitializeApp()
    → LaunchDatabase()：连接 MySQL、创建项目数据库、设置连接池
    → 商品初始化、任务初始化、分类迁移
    → 装配 Repository、Service、Handler
  → router.SetupRouter(app)
  → HTTP Server.ListenAndServe()
```

`go run .` 编译并启动当前 Go 包。它本身不会自动读取 .env，是 `backend/config/config.go` 中的代码调用 `godotenv.Read(".env")`。

在 backend 目录启动时，当前工作目录为 backend，因此读取 backend/.env。系统环境变量优先；未设置时读取文件，再按代码使用默认值。必需配置仍会校验，不能假设省略任何配置都能正常启动。

线上配置则由部署脚本和 Compose 传入：

```text
服务器 /opt/lesson-fullstack/.env
  → release.sh 使用 --env-file .env
  → compose.yaml 的 environment 注入 API 容器
  → Go 使用 os.LookupEnv() 读取环境变量
```

Go 不需要知道服务器 .env 的路径，也不需要把真实配置文件放进镜像。修改服务器文件后，需要通过 Compose 更新容器才能使用新环境变量；只改文件不会改变已运行进程的环境。

## 12. 新电脑为什么能自动建库建表，旧数据会被覆盖吗

前提是 MySQL 已启动、地址和账号密码正确，并且账号具有所需的建库、建表及迁移权限。程序不会替你安装或启动 MySQL。

迁移由 `backend/bootstrap/` 显式管理，`lesson_migrations` 记录已完成的版本：

| 版本 | 内容 |
|---|---|
| 1 | 初始化商品结构并首次插入商品演示数据 |
| 2 | 初始化任务表、看板版本和任务演示数据 |
| 3 | 建立分类表，为旧商品的中文分类补充 category_id |

`backend/migration/` 保存演示数据 SQL，main.go 通过 go:embed 将其编译进程序。新环境自动初始化，已完成的种子迁移不会在每次启动时重插，用户修改或删除的商品不会被种子覆盖或补回。

版本 3 支持从旧的中文分类升级。商品接口与业务改为使用 category_id；旧 category 列保留用于升级兼容，不再用于日常查询或保存。迁移和实体字段是两回事：当前项目没有依靠 GORM 自动猜测并修改所有表结构。

## 13. 对照代码检查数据流

完成阅读后，可用以下问题确认理解：

- 新增时 categoryId 从哪个下拉选项产生，后端在哪里验证存在性？
- HTTP 请求中的 priceCents 与输入框中的 price 为什么不同？
- status 没传与传 0，Go 如何区分？
- 库存更新为 0 时，Repository 为什么仍然会写入？
- SKU 重复由哪一层最终保证，中文错误提示在哪里转换？
- 保存成功后，列表更新靠接口返回新商品，还是重新查询？
- 本地 .env 与服务器 .env 分别由谁读取？

全栈联调的关键是沿请求追踪字段和状态：输入、请求、校验、存储、响应、页面更新。掌握这条链路后，再扩展其他业务模块会更容易定位问题。
