## 三层组件关系

```text
Element Plus / SortableJS / VueUse / dayjs
       ↓ 基础能力
Vben PageHeader / useSortable / formatDate
       ↓ 项目已有封装
TaskCard / TaskBoard / TaskFormDrawer / useTaskBoard
       ↓ 任务业务约定
任务看板页面：筛选、统计、组织操作、对接 Gin
```

- **三方组件**解决输入、日期选择、抽屉、提示、拖拽等通用交互。
- **框架封装**提供本项目统一的接入方式，先读实际实现再使用。例如 `useSortable` 返回异步初始化函数，实例仍需要调用方销毁。
- **业务组件**表达任务的字段和行为。TaskCard 接收一条 Task，发出 edit/remove/copy；它不直接调用 API。
- **组合函数**集中处理看板读取、版本、保存中状态与错误恢复，避免散落在三个列组件中。

## 重点一：抽屉是业务表单，不是直接修改卡片对象

页面只决定 `editing`、`initialStatus`、`open`；抽屉建立独立的 reactive 草稿。

```text
页面 task + modelValue + initialStatus → 抽屉
打开时复制字段 → nextTick → clearValidate
保存：submitting=true → validate → TaskInput → props.save
成功：关闭抽屉；失败：保留输入
finally：恢复按钮
```

抽屉调用的 `save` 由页面传入，最终进入 useTaskBoard.save。因此任务请求与版本统一在组合函数里管理，抽屉不再维护另一份看板。

日期是可选字段，日期选择器清除后可能给出 null，提交时用 `form.dueDate || ''` 归一。这里是字符串字段；不要把这写法照搬到状态 0 或金额 0 上。商品模块保留下架状态 0，正好可作为对照。

## 重点二：拖拽有 DOM 和数据两份状态

`useSortable` 来自 `@vben/hooks`，底层使用已经安装的 SortableJS，没有新增拖拽依赖。

关键选项：

- `group: 'lesson-task-board'`：三个列允许相互移动。
- `handle: '.drag-handle'`：从手柄拖动，点击标题仍能编辑。
- `draggable: '.task-card'`：只有任务卡参与排序。
- `data-id`：稳定数据库 ID；`data-status`：目标列的业务状态。
- `disabled`：加载、保存、错误未恢复、筛选条件存在时禁用。

onEnd 的顺序不能颠倒：

```text
读取 id、目标 status 和下一张卡的 beforeId
→ 把 Sortable 移动过的真实 DOM 放回原处
→ emit('move', {id, status, beforeId})
→ Vue 依照新任务数组渲染
→ Gin 保存，返回权威快照
```

为什么先恢复 DOM：Vue 仍按旧虚拟节点追踪卡片，若直接保留库移动的节点再更新数组，可能出现重复、位置错乱或删除错误。

为什么传 `beforeId`，不直接传目标下标：下标只代表当前画面的位置；稳定 ID 更适合接口校验。0 表示追加到目标列末尾。筛选时只看到部分任务，所以本课明确禁用拖拽，仍允许抽屉编辑状态。

异步初始化完成时检查组件是否已经卸载；卸载时销毁全部 Sortable 实例，避免反复进菜单累积事件。

官方 API 可参考 [SortableJS 文档](https://github.com/SortableJS/Sortable)。本项目具体用法以当前封装和组件源码为准。

## 重点三：乐观更新必须有失败路径

`useTaskBoard` 中，读取和写入分别使用 loading、pending。保存期间拒绝第二次写入。

```text
保留 previous 看板快照
→ 本地 applyTaskMove，立即移动卡片
→ 携带 version 请求 API
→ 成功：采用服务器 items + version
→ 失败：恢复 previous，再 GET 最新看板
→ 重读失败：显示重试入口，禁用写入
```

超时不意味着服务端一定没有写入，所以恢复本地快照后还要重读。409 表示当前页面版本已旧：后端不执行这次写入，前端同步最新看板，编辑草稿继续保留。用户应核对最新内容再决定是否再次保存。

requestId 只用于阻止旧查询覆盖新结果；它解决不了多客户端写入冲突。后端 version + 事务解决另一类问题，两者不要混淆。

运行可控测试，不依赖现场网速恰好变慢：

```sh
# frontend 目录
corepack pnpm exec vitest run apps/admin/src/composables/use-task-board.test.ts apps/admin/src/views/tasks/task-meta.test.ts
```

## 重点四：派生状态用 computed

本课堂单看板最多 200 条任务，GET 返回完整快照，所以筛选在前端进行，三列、统计与排序都基于同一份数据。**商品模块是服务端分页，不能照搬这个前端过滤策略。**

- 顶部总任务数、进行中、逾期数、完成率基于完整看板。
- 三列显示筛选后的任务，并明确提示“筛选结果 x / y”。
- 逾期条件：未完成、设置了截止日期、日期早于浏览器本地当天。今天截止不算逾期；完成任务不再标红。
- 完成率：已完成 / 全部，空看板返回 0%，避免除以 0。

日期仅作为日历日，不是某个时区的瞬间；如果升级为跨时区截止时间，应另行明确 UTC 与显示时区约定。

## 课前验收与故障预案

1. 启动 Go 与前端，登录并切换两项菜单。
2. 看板应有 9 条种子任务（若讲师已增删则以实际为准），三个阶段都有数据。
3. 用自己创建的 CLASS-* 任务演示，结束后清理；不要通过删迁移记录重置。
4. 请求 `/api/tasks` 应返回 version，写入后 version 增加；无需改商品接口。
5. 若拖拽不可用，先检查是否正在筛选/保存或加载失败；可在抽屉中修改状态。
6. 若需要演示失败回滚，可以暂时停掉本项目 Go 后拖动测试卡；恢复 Go 后重新登录。不能用其他业务进程做故障实验。
7. 服务已停止时保留旧卡片只是为了帮助恢复上下文，不表示数据仍是最新；此时界面会禁用写入。

完整接口与已执行验证见 `07-任务接口与验收.md`。

## 课后练习

- 给筛选条件加 URL 同步：支持刷新还原，并避免 watch 循环。
- 增加负责人选项接口：将现在的自由文本替换成真实用户 ID，说明迁移与显示名称的区别。
- 扩展多项目看板：先解释为什么需要把全局 version、200 条限制和数据加载范围改成项目级，再实现。
